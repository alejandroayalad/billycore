# BillyCore — Data Model

This document defines the physical SQLite schema used by BillyCore.

It defines:

- tables
- columns
- SQLite types
- nullability
- foreign keys
- indexes
- migrations

It does not define the financial domain. See [DOMAIN.md](DOMAIN.md).

It does not decide why BillyCore uses SQLite. See [ARCHITECTURE.md](ARCHITECTURE.md).

> Database constraints are a backstop. Domain rules remain enforced by domain code.

Repositories return domain types directly. BillyCore does not have a separate
persistence model or mapper layer.

---

## 1. Purpose and boundaries

BillyCore stores three main domain concepts:

- Evidence
- Claim
- Transaction

Evidence is what Billy observed. Claims are interpretations of Evidence. Transactions
are the financial events Billy currently believes exist.

The schema preserves the links between these concepts so every Transaction can be
traced back to Evidence.

> The database must not become a second domain model.

---

## 2. Conventions

### IDs

IDs are UUIDs generated by the application and stored as `TEXT`.

```sql
id TEXT
```

The schema does not depend on a specific UUID version.

IDs are never SQLite auto-increment integers, because IDs also appear in the public API.

### Timestamps

Timestamps are stored as UTC RFC 3339 text.

```
2026-08-23T18:46:00.000Z
```

SQLite has no native timestamp type. Using `TEXT` keeps timestamps readable, sortable,
and compatible with the API representation.

Application code is responsible for parsing and validating timestamps.

### Enums

Domain enums are stored as uppercase `TEXT`.

```
ACTIVE  SUPERSEDED  OUTFLOW  INFLOW  PENDING  SETTLED  HIGH  MEDIUM  LOW
```

The database does not define the allowed enum values with `CHECK` constraints. The
domain owns those rules.

### Money

Money uses integer minor units. `800.50 MXN` is stored as:

```
amount_minor = 80050
currency     = "MXN"
```

Money is never stored as `REAL`.

The application enforces that the amount is unsigned and that currency exists wherever
Money exists.

### Missing values

Missing domain information is stored as `NULL` or, for Claim fields, by the absence of a
row.

Missing information must not be represented as fake values such as `"UNKNOWN"`, `0`, or
`""` — unless `UNKNOWN` is itself a real domain enum value, such as
`financial_status = UNKNOWN`.

## 3. Domain → schema mapping

| Domain concept | Schema |
|---|---|
| Evidence | `evidence` |
| Claim | `claims` |
| Claim provenance | `claim_evidence` |
| Claim fields + confidence | `claim_fields` |
| Transaction | `transactions` |
| Transaction provenance | `transaction_evidence` |
| Money | integer `amount_minor` + `currency` |
| Confidence | `claim_fields.confidence` |
| AccountIdentifier | text value, not a table |
| SourceReference | columns on `evidence` |
| Domain event | `domain_event` |
| Reconciliation candidate | unresolved; see Open Questions |

Several domain concepts deliberately do not become tables. There is no `account`,
`merchant`, `currency`, or `user` table.

A Source also does not need a domain table in v1. Evidence stores its source type and
source reference directly.

## 4. Schema

BillyCore applies these pragmas when it opens the database, per ARCHITECTURE.md §7:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = <configured>;
```

`journal_mode` is persistent — it is stored in the database file and survives reopening
— while `foreign_keys` and `busy_timeout` are per-connection and must be set on every
connection BillyCore opens.

ARCHITECTURE.md requires a busy timeout but does not fix a value, so none is invented
here.

### 4.1 Evidence

Evidence preserves the source artifact Billy observed.

```sql
CREATE TABLE evidence (
    id                  TEXT PRIMARY KEY NOT NULL,
    source_id           TEXT NOT NULL,
    source_type         TEXT NOT NULL,
    source_reference    TEXT NOT NULL,
    raw_content         BLOB,
    observed_at         TEXT NOT NULL,
    created_at          TEXT NOT NULL,
    processing_stage    TEXT NOT NULL,
    attempts            INTEGER NOT NULL DEFAULT 0,
    last_error          TEXT,
    locked_until        TEXT,
    UNIQUE (source_id, source_reference)
) STRICT;
```

**`source_id`** identifies the specific configured Source instance — for example
`gmail_primary`. It is infrastructure, not domain: two Gmail accounts are two Sources
and share a `source_type`. There is no Source table and no foreign key in v1.

**`source_type`** identifies the kind of Source — for example `GMAIL` or
`BANK_STATEMENT`.

**`source_reference`** is a stable reference to the original source artifact. For Gmail
it is the message id.

**`UNIQUE (source_id, source_reference)`** makes ingestion idempotent. This is the
storage form of the decision in ARCHITECTURE.md §5:

> Evidence carries a `source_artifact_key`, unique per Source. Ingestion is an upsert on
> that key. The same email fetched twice produces one row.

Ingestion is therefore an upsert:

```sql
INSERT INTO evidence (...) VALUES (...)
ON CONFLICT (source_id, source_reference) DO NOTHING;
```

> This is a deduplication mechanism, not an answer to a domain question. *Is this the
> same artifact?* is an ingestion concern, settled here. *Do these two different
> artifacts describe the same Transaction?* is reconciliation, and it stays with the
> domain.

**`raw_content`** holds the original source bytes when Billy stores the artifact itself.
It can be `NULL` when `source_reference` is the preserved reference.

**`observed_at`** is when Billy observed or received the Evidence. **`created_at`** is
when Billy stored it.

The remaining columns belong to the processing pipeline, not the Evidence domain object.

### 4.2 Claims

A Claim is an interpretation derived from Evidence.

```sql
CREATE TABLE claims (
    id                      TEXT PRIMARY KEY NOT NULL,
    state                   TEXT NOT NULL,
    superseded_by_claim_id  TEXT,
    created_at              TEXT NOT NULL,
    updated_at              TEXT NOT NULL,
    FOREIGN KEY (superseded_by_claim_id)
        REFERENCES claims(id)
        ON DELETE RESTRICT
) STRICT;
```

Examples of `state`: `PROPOSED`, `ACTIVE`, `SUPERSEDED`, `REJECTED`.

The database does not validate these values. The domain does.

**`superseded_by_claim_id`** points from the old Claim to the new one, matching the
`superseded_by` field in the API contract:

```
Claim A
    state                  = SUPERSEDED
    superseded_by_claim_id = Claim B
```

Historical Claims are preserved.

### 4.3 Claim provenance

Claims must remain traceable to Evidence.

```sql
CREATE TABLE claim_evidence (
    claim_id       TEXT NOT NULL,
    evidence_id    TEXT NOT NULL,
    PRIMARY KEY (claim_id, evidence_id),
    FOREIGN KEY (claim_id)
        REFERENCES claims(id)
        ON DELETE RESTRICT,
    FOREIGN KEY (evidence_id)
        REFERENCES evidence(id)
        ON DELETE RESTRICT
) STRICT;
```

A join table is used instead of putting `evidence_id` directly on `claims`. This avoids
making a storage decision about whether a Claim may eventually use more than one piece
of Evidence.

The domain still decides the allowed cardinality.

### 4.4 Claim fields

A Claim contains interpreted fields. Each field carries its own confidence.

```sql
CREATE TABLE claim_fields (
    claim_id       TEXT NOT NULL,
    field_name     TEXT NOT NULL,
    value_int      INTEGER,
    value_text     TEXT,
    confidence     TEXT NOT NULL,
    PRIMARY KEY (claim_id, field_name),
    FOREIGN KEY (claim_id)
        REFERENCES claims(id)
        ON DELETE RESTRICT,
    CHECK (
        (value_int IS NOT NULL AND value_text IS NULL)
        OR
        (value_int IS NULL AND value_text IS NOT NULL)
    )
) STRICT;
```

The `CHECK` only protects the physical representation. It does not define financial
meaning.

| `field_name` | `value_int` | `value_text` | `confidence` |
|---|---|---|---|
| `amount_minor` | 80000 | `NULL` | `HIGH` |
| `currency` | `NULL` | `MXN` | `HIGH` |
| `merchant` | `NULL` | `Amazon` | `MEDIUM` |
| `account_identifier` | `NULL` | `1234` | `LOW` |
| `direction` | `NULL` | `OUTFLOW` | `HIGH` |
| `financial_status` | `NULL` | `PENDING` | `HIGH` |
| `occurred_at` | `NULL` | `2026-08-23T…Z` | `MEDIUM` |
| `tracking_key` | `NULL` | `NU3AG95…` | `HIGH` |
| `counterparty` | `NULL` | `A. García` | `HIGH` |

The vocabulary is nine names, a closed set the domain owns (D33, D36, D61):

- **`occurred_at`** is when the artifact said the event happened, UTC RFC 3339.
  It can be absent — a card-payment email states no date, and a statement row
  states a day only — and its absence is what the Transaction fallback fills
  (§4.5). It is never present with a `null` value.
- **`tracking_key`** is the SPEI `Clave de rastreo`, kept verbatim, present where
  the artifact states one. A statement states one on almost every SPEI movement,
  in both directions — it is no longer an outflow-only field — so it is the
  strongest reconciliation signal (§6). It has no Transaction column: a reader
  reaches it through `claim_transaction` (D66).
- **`counterparty`** is the person or the institution on the other side of a
  movement (D61). It is not the merchant: a merchant is a place where something
  was bought, and a counterparty is the other side of a transfer. It carries the
  reserved value `urn:billy:self` when both sides are the user (D62, D65), which
  marks an internal movement.

If Billy has no Claim for a field, no row exists. This preserves the difference between
*account is missing* and *account = 1234 with LOW confidence*.

### 4.5 Transactions

A Transaction is BillyCore's current representation of a financial event.

```sql
CREATE TABLE transactions (
    id                      TEXT PRIMARY KEY NOT NULL,
    amount_minor            INTEGER,
    currency                TEXT,
    merchant                TEXT,
    counterparty            TEXT,
    account_identifier      TEXT,
    direction               TEXT NOT NULL,
    financial_status        TEXT NOT NULL,
    reconciliation_state    TEXT NOT NULL,
    transaction_state       TEXT NOT NULL,
    occurred_at             TEXT NOT NULL,
    created_at              TEXT NOT NULL,
    updated_at              TEXT NOT NULL
) STRICT;
```

**`counterparty`** is nullable and holds the person or the institution on the other
side of the movement, preserved from the Claim (D66). It is not the merchant. It carries
the reserved value `urn:billy:self` for an internal movement — money between the user's
own accounts (D62, D65). `transaction_state` is the lifecycle from D49.

```
direction:             INFLOW · OUTFLOW
financial_status:      UNKNOWN · PENDING · SETTLED · REVERSED
reconciliation_state:  UNRECONCILED · RECONCILED · CONFLICTED
```

The domain validates these values.

**Money is nullable.** A Transaction may exist without Money when the available Evidence
does not support an amount. When `amount_minor` exists, `currency` must also exist.

This invariant is enforced by the domain, not by a database `CHECK` constraint. It
follows DOMAIN.md §4: unsupported financial facts are forbidden, and currency is required
wherever Money exists. Recording an amount Billy cannot support would be a fabricated
financial fact; recording one without its currency would be meaningless.

**`occurred_at`** is always populated. When Billy knows the event time, it uses that
time. When the event time is unknown, Billy uses the earliest `observed_at` from its
Evidence. This gives Transactions a stable value for cursor pagination.

The fallback is calculated before writing the Transaction. It is not calculated inside
SQL queries.

**Internal movements.** A Transaction whose `counterparty` is `urn:billy:self` is a
movement between the user's own accounts — a Cajita or a `dinero de respaldo` movement
(D55, D63). It is a real Transaction: it keeps its true direction, it stays in the
history, and its Evidence is not hidden. It is only excluded from the income and spending
totals, because the money did not enter or leave the user's control (D67). The totals
read model, at `GET /v1/transactions/summary`, is where that exclusion happens.

### 4.6 Transaction provenance

A Transaction can be supported by multiple pieces of Evidence.

```sql
CREATE TABLE transaction_evidence (
    transaction_id    TEXT NOT NULL,
    evidence_id       TEXT NOT NULL,
    PRIMARY KEY (transaction_id, evidence_id),
    FOREIGN KEY (transaction_id)
        REFERENCES transactions(id)
        ON DELETE RESTRICT,
    FOREIGN KEY (evidence_id)
        REFERENCES evidence(id)
        ON DELETE RESTRICT
) STRICT;
```

The domain requires every Transaction to have at least one Evidence link. SQLite does
not try to enforce that cross-table rule.

The repository creates the Transaction and its provenance links in one database
transaction.

### 4.7 Domain events

Meaningful business facts, in the order they occurred.

```sql
CREATE TABLE domain_event (
    seq         INTEGER PRIMARY KEY,
    type        TEXT NOT NULL,
    payload     TEXT NOT NULL,
    occurred_at TEXT NOT NULL
) STRICT;
```

**`seq`** is the cursor used by `GET /v1/events`. As an `INTEGER PRIMARY KEY` it is
SQLite's rowid, assigned monotonically.

**`payload`** contains JSON serialized by application code. This is the one place JSON
is reasonable: an event payload is written once and read whole, never queried by field.

**`type`** holds the event names defined in DOMAIN.md §8. The database does not validate
them.

Events are append-only. They are never updated and never deleted.

> A domain event must be persisted in the same SQLite transaction as the domain change
> that produced it. An event that describes a change that did not commit is a lie about
> the domain, and a change that commits without its event is invisible to every
> consumer.


Indexes exist for known queries. Indexes are not added only because a column looks
important.

### Evidence lookup by source reference

No explicit index is declared. `UNIQUE (source_id, source_reference)` on `evidence`
already creates one, and it serves both the ingestion upsert and lookup of Evidence from
a source artifact.

### Evidence pipeline scan

Used by background processing to find Evidence in a processing stage.

```sql
CREATE INDEX idx_evidence_pipeline_scan
ON evidence(processing_stage, observed_at, id);
```

```sql
SELECT *
FROM evidence
WHERE processing_stage = ?
  AND (locked_until IS NULL OR locked_until <= ?)
ORDER BY observed_at, id
LIMIT ?;
```

### Claims from Evidence

```sql
CREATE INDEX idx_claim_evidence_by_evidence
ON claim_evidence(evidence_id, claim_id);
```

Used to find the Claims derived from Evidence.

### Integer Claim values

```sql
CREATE INDEX idx_claim_fields_int_value
ON claim_fields(field_name, value_int, claim_id)
WHERE value_int IS NOT NULL;
```

Used for fields such as `amount_minor`.

### Text Claim values

```sql
CREATE INDEX idx_claim_fields_text_value
ON claim_fields(field_name, value_text, claim_id)
WHERE value_text IS NOT NULL;
```

Used for fields such as currency, merchant, account identifier, direction, and financial
status.

### Transaction cursor pagination

```sql
CREATE INDEX idx_transactions_cursor
ON transactions(occurred_at DESC, id DESC);
```

This supports API pagination using `(occurred_at, id)` as the cursor.

### Transactions supported by Evidence

```sql
CREATE INDEX idx_transaction_evidence_by_evidence
ON transaction_evidence(evidence_id, transaction_id);
```

Used when Billy needs to find the Transaction associated with a piece of Evidence.

## 6. Aggregate boundaries

Evidence, Claim, and Transaction are separate aggregate roots. The database does not
create one large aggregate around them.

Foreign keys preserve references between aggregates. They do not define domain behavior.

### Foreign keys that exist

```
claim_evidence.claim_id             → claims.id
claim_evidence.evidence_id          → evidence.id
claim_fields.claim_id               → claims.id
claims.superseded_by_claim_id       → claims.id
transaction_evidence.transaction_id → transactions.id
transaction_evidence.evidence_id    → evidence.id
```

### Foreign keys that deliberately do not exist

```
currency
merchant
account_identifier
source_id
source_type
source_reference
```

These are values or external references, not v1 entities.

### Cascade policy

v1 uses `ON DELETE RESTRICT` for domain references.

BillyCore does not silently delete provenance because another row was deleted.

Whether Evidence itself may ever be deleted is still a domain question. Until that is
decided, `RESTRICT` is the safe storage behavior.

## 7. Pipeline columns

Evidence contains four infrastructure fields:

```
processing_stage
attempts
last_error
locked_until
```

They exist because ingestion and extraction need durable work state. They are not part
of the Evidence domain object.

`processing_stage` uses the vocabulary defined in ARCHITECTURE.md §5, and only that
vocabulary:

```
RECEIVED  →  EXTRACTED  →  RECONCILED
```

**Retry is not a processing stage.** Evidence that failed extraction stays in the stage
it was in; retry behavior lives in `attempts`, `last_error`, and `locked_until`. Adding
`RETRYING` or `FAILED` as stages would put pipeline failure into the same column as
pipeline progress, and DOMAIN.md §5 already rules those states out of the domain
entirely.

Processing concepts do not change what the Evidence means.

Repositories that return Evidence domain types do not expose these fields as Evidence
properties. Infrastructure-specific repository operations may update them directly:

```
claim evidence for processing
mark processing attempt
store processing error
release processing lock
```

The Evidence payload itself remains immutable.

## 8. Migrations

Database migrations are embedded in the BillyCore binary, numbered, forward-only, and
run automatically at startup.

```
001_initial.sql
002_add_example_index.sql
003_add_example_column.sql
```

BillyCore tracks the current migration with `PRAGMA user_version`.

```
open database
    ↓
apply pragmas
    ↓
read user_version
    ↓
run missing migrations in order
    ↓
update user_version
    ↓
start BillyCore
```

Each migration runs inside a SQLite transaction. If a migration fails, BillyCore does
not start.

There are no automatic down migrations.

## 9. Deliberately not modeled

**Account.** There is no `accounts` table. BillyCore currently stores an
`AccountIdentifier`. A full Account entity requires stronger identity rules across
Sources.

**Currency.** There is no `currencies` table. Currency is stored as a code such as `MXN`
or `USD`.

**Merchant.** There is no `merchants` table. Merchant normalization does not justify a
Merchant entity in v1.

**User.** There is no `users` table. BillyCore v1 is self-hosted for one user.

**Transaction relationships.** There is no refund, transfer, or reversal relationship
table yet. The domain already recognizes that Transactions may have relationships, but
their representation is still an open question. The schema must not invent that answer.

> **Known mismatch.** DOMAIN.md has not yet defined the physical representation of
> Transaction relationships. API.md currently exposes `Transaction.relationships` before
> that domain decision has been made.
>
> The domain question is settled first. Then either the relationship table is added, or
> `relationships` is removed or changed in API.md. A schema is not invented here only to
> satisfy the current API document.

**Reconciliation candidates.** A `reconciliation_candidate` pairs two Transactions and
records a status. `left_ref` and `right_ref` are `transactions.id`; the status is
`MATCH`, `NO_MATCH` or `AMBIGUOUS` (DOMAIN.md §6, D69). The Transaction is Billy's
representation of one event and carries every signal the comparison uses, so the
candidate points at it rather than at a Claim or a piece of Evidence.

```sql
CREATE TABLE reconciliation_candidate (
    id          TEXT PRIMARY KEY NOT NULL,
    left_ref    TEXT NOT NULL,
    right_ref   TEXT NOT NULL,
    status      TEXT NOT NULL,
    created_at  TEXT NOT NULL,
    FOREIGN KEY (left_ref)  REFERENCES transactions(id) ON DELETE RESTRICT,
    FOREIGN KEY (right_ref) REFERENCES transactions(id) ON DELETE RESTRICT
) STRICT;
```

The table and its indexes are added by a migration when reconciliation is built. What a
`MATCH` does to the two Transactions — one survives and the other is retired through
`superseded_by_transaction_id` (D49), or both stay and are linked — is the remaining
decision.

## 10. Open questions

**1. ~~What does a reconciliation candidate reference?~~ Closed by D69.**

`reconciliation_candidate.left_ref` and `right_ref` are `transactions.id` (§9). The
Transaction carries every signal DOMAIN.md §6 compares, and the rest of the system
already speaks in Transaction ids. A Claim reference or an Evidence reference was
rejected: the first fights the Transaction-centric API, and one statement PDF is one
Evidence with about 180 movements, so an Evidence pair cannot say which movement matched.

**2. Can Evidence be deleted?**

Current schema policy is `ON DELETE RESTRICT`, which preserves provenance. The final
deletion behavior depends on the domain decision about Evidence deletion.

**3. How are Transaction relationships represented?**

Refunds, partial refunds, transfers, and reversals may require explicit Transaction
relationships. Their representation belongs in the domain first. No relationship table
is created until that decision exists.

---

## Initial schema

The first migration consists of the finalized tables and indexes above. The
reconciliation schema — the `reconciliation_candidate` table of §9 — is added by its own
migration when reconciliation is built (D69).

> SQLite stores the domain. It does not define the domain.
